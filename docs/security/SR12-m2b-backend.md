## Confirmed protections (each probed unless marked "read")

- **Workspace isolation.** All of these return 404 from another workspace: `GET/DELETE /documents/{id}`, account documents, org-proposals list, org-chart, accept, reject, `PUT /contacts/{id}/title-class`, `POST /orgchart/propose` for a foreign account. Upload to a foreign account: 404. Foreign `deal_id`: 404; a deal of another account of the same workspace: 422. `by_id` of a user from another workspace: 404. Accept with a foreign `manager_id`: 422 (not a candidate / differs from the proposed manager); candidates and `_check_manager` are account-scoped. Company documents and listings filter on `workspace_id` (read).
- **PDF.** Encrypted (even empty user password) refused; page cap 300 enforced (also with a lying `/Count`); char cap enforced; flate bomb, deep nesting, cyclic or exponential forms, bad xref, filter chains and huge boxes all end in a clean 422 within about a second and below 0.5 GB. Gap: SR12-02.
- **Text.** Magic-number sniffing (a `%PDF` body named `.txt`, NUL bytes, UTF-16 are refused); UTF-8 then Latin-1 works; BOM stripped; NUL and surrogates scrubbed; file name sanitised (`../../etc/passwd.txt` stored as `passwd.txt`); offsets index the final stored text and every evidence excerpt equals `document.text[char_start:char_end]` (verified for 5 patterns including text with NBSP, bidi and control characters). The excerpt is checked again before a finding is kept (read).
- **Multipart.** The allow-list matches only `/files` and `/accounts/{36 chars}/documents` for POST; the documents route gets `transcript_max_bytes + 64 KB` (5 MB + 64 KB), the files route keeps its own limit, everything else 256 KB JSON only. Origin/X-DataForce and Host guards still apply to the upload (403 without them). Multipart sent to a JSON route or `/themes/run`: 415. Chunked 10 MB body: 413. 1500 form fields: 400. Oversized title: 422. A second `file` part is ignored.
- **Regex DoS.** `_SPEAKER`, the sentence splitter and the 13 meeting patterns were run on 1 M-character adversarial inputs (no colon, nested words, 1 M spaces after dots, 1 M `(`, whitespace runs near "report"): all finished in under 0.35 s; chunks are capped at 1200 chars; name alternation grows linearly (3000 contacts x 100 KB: 0.7 s).
- **Proposals.** A cycle through accepted proposals is refused (X->Y accepted, then Y->X: 422 "would create a cycle"); decided proposals cannot be re-accepted or rejected (422); accept/reject take the account advisory lock before re-reading the status; manual `set_reports_to` clears `reports_to_proposal_id`; the chart shows the origin only when the link still matches the accepted proposal; a manual link is never overwritten by a run; rejected reports_to pairs are not re-proposed; meeting findings only come from chunks whose `contact_id` belongs to the same account.
- **Title AI.** Only the normalised title is sent (test: names never in prompts); `</source>` and look-alikes are neutralised by `wrap_sources`; cache is workspace-scoped; the call cap is enforced per run; manual classes are never overwritten; no AI configured gives a flag, not a call; `preview` is dictionary-only, length-capped at 200 and fast on adversarial titles.
- **Logs.** No `log`/`print` call in any in-scope file; the global handlers log the exception type only.
- **CRM flows tables.** `meetings`, `meeting_themes`, `deal_theme_flags` and `contacts` queries are all filtered by `workspace_id` (documents, chunks, themes, deals); the latest run id is workspace-scoped; no document text is exposed (read).
- **Themes shell.** Body model is `extra="forbid"`, `k` bounded 2..30; every query goes through `ws.id`.

## Residual risks

- Naming themes with the AI sends customer excerpts (they may contain names or personal data) to the configured provider; wrapped as untrusted, but that is text leaving the machine, unlike the local TF-IDF/NMF step. Document it in the privacy notes (SR12-03 policy applies).
- Transcript authorship is untrusted: anyone who can upload can write "Marie Dupont: je reporte à X". Only the human accept step protects the org chart; keep the excerpt visible and show the document and speaker in the accept UI.
- `by_id` on accept/reject is caller-supplied (no login before M3), so decisions can be attributed to any user of the workspace.
- A document hash is stored but duplicates are not rejected (double-counting in themes).
- A contact rename does not rebase old chunk attributions (`contact_id` stays on the old speaker label).

### Residual risks after the fixes

- Mentions of the erased person in other people's notes, in titles of other documents (only an exact full or first + last name is masked), or by first name or surname alone, nicknames and misspellings stay in the text: the redaction is name-pattern based. Same residual as M1 for notes.
- A rename of a contact does not redact or re-attribute older transcripts, and the old name is not masked when the person is later erased under the new name.
- Themes already built from the chunks (excerpts, labels, AI-named themes sent to a provider) are owned by the themes module and are not rewritten here; rerun the themes after an erasure.
- The title AI limits are per process (not shared between workers, reset on restart).
- Stale-accept protection relies on the baseline recorded at proposal time; the check and the write run under the account advisory lock.
