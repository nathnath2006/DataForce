## A. Accounts (backend builder A)

### A1. Roles stay as they are
- **Superadmin**: `user_account.is_admin`, the first setup account, sees every workspace.
- **Workspace admin**: a `membership.role = 'admin'` membership. That person administers that
  workspace only and never sees another.
- **Rep**: a `membership.role = 'rep'` membership.

### A2. Creation codes (superadmin only)
Table `creation_code`:
- `id`
- `code_hash` (sha256 of the code; never store the code)
- `label`
- `created_by` → user_account
- `created_at`
- `expires_at` (default 14 days)
- `max_uses` (default 1)
- `uses`
- `revoked_at`

The code is 20+ random url-safe characters, shown **once** at creation.

API (superadmin):
- `GET /api/admin/creation-codes` (no codes shown, only label, uses and dates)
- `POST /api/admin/creation-codes` `{label, expires_in_days?, max_uses?}` → `{id, code, …}`, the code
  this one time only
- `POST /api/admin/creation-codes/{id}/revoke`

### A3. Join tokens (workspace admin, or superadmin)
Table `join_token`:
- `id`
- `workspace_id`
- `token_hash`
- `role` (`rep` | `admin`)
- `label`
- `created_by`
- `created_at`
- `expires_at` (default 7 days)
- `max_uses` (default 1, up to 50)
- `uses`
- `revoked_at`

API (admin of `{ws}`):
- `GET /api/w/{ws}/join-tokens`
- `POST /api/w/{ws}/join-tokens` `{role, label, expires_in_days?, max_uses?}` → token shown once
- `POST /api/w/{ws}/join-tokens/{id}/revoke`

A workspace admin can only make tokens for their own workspace, and cannot make `admin` tokens
unless they are an admin of it.

### A4. Sign-up (public, rate-limited like login: per client address and per email)
`POST /api/auth/signup` `{email, display_name, password, mode: "create"|"join", code}`:
- The password always follows the normal password rule; never empty, even on loopback.
- **`create`**: the creation code must be valid (not expired, revoked or used up).
  - Create the account (not superadmin) with `workspace_credits = 1`, a new
    `user_account.workspace_credits INT NOT NULL DEFAULT 0`.
  - Count one use of the code and sign the person in.
  - Then the UI sends them to `/welcome`.
  - `POST /api/workspaces` is now allowed for a superadmin **or** an account with
    `workspace_credits > 0`. It takes one credit and makes that person `admin` of the new workspace.
  - Test workspaces still go one fill at a time, with the quota guard.
- **`join`**: the join token must be valid.
  - Create the account, add the membership with the token's role, count one use, sign in.
  - If the email already has an account: answer the same generic error as a wrong code. This
    leaks nothing. Joining with an existing account is done after signing in, below.
- `POST /api/auth/join` `{token}`, signed in: adds the membership for an existing account.
- Every failure gives one generic message, "invalid or expired code", with the same timing. Codes
  and tokens are compared by hash in constant time.
- Hosted mode: `/api/auth/status` also returns `signup_enabled: true`. Local mode: the same.

### A5. Email (Gmail SMTP)
New settings:
- `SMTP_HOST` (default `smtp.gmail.com`)
- `SMTP_PORT` (default 587, STARTTLS required)
- `SMTP_USERNAME`
- `SMTP_PASSWORD` (SecretStr; a Secret Manager secret on Cloud Run, never logged)
- `MAIL_FROM` (default = `SMTP_USERNAME`)
- `MAIL_FROM_NAME` (default "DataForce")

`app/services/mailer.py`:
- `send(to, subject, text, html=None)` with a 10 s timeout.
- Called from a background thread, so a slow SMTP server never delays a request.
- When SMTP is not configured: log a warning and keep today's behaviour (the reset link goes to the
  server log), so local dev works without email.

Uses:
- **Password reset**: `/api/auth/forgot` emails the link `{origin}/reset?token=…`. Its answer stays
  "accepted" whatever happens.
- **Optional join-token email**: `POST /api/w/{ws}/join-tokens` with `email_to` sends the join
  link `{origin}/signup?token=…`.

Plain, short texts in English. No tracking, no images.

### A6. Tests
Code and token lifecycle:
- expiry, revoke and max uses
- hash only in the database
- shown once

Sign-up:
- create with a code → credit → POST /workspaces → workspace admin, sees only their workspace
- join → rep, sees only that workspace

Security:
- a wrong code or an existing email gets the same generic error
- rate limits apply
- a workspace admin cannot make tokens for another workspace, nor creation codes
- the mailer is stubbed in tests: the forgot flow sends one email, and nothing is sent when SMTP is
  off
- the SMTP password never appears in logs or errors

Then run `make api-types`.

## B. Limits, usage, models, task status (backend builder B)

### B1. Admin-editable limits
Port `backend/app/services/limits.py` and the `setting_override` and `setting_override_audit`
tables from branch `wip/m5-wave3` (`git show wip/m5-wave3:<path>`) into `0014_limits_usage`. Do
**not** take its mailbox changes. The limits service is the one place the code reads a limit;
replace direct `settings.<limit>` reads for the keys in its allow-list.

API:
- `GET /api/admin/limits`: global, superadmin.
- `PUT /api/admin/limits/{key}` `{value|null}`: global, superadmin.
- `GET /api/w/{ws}/admin/limits` and `PUT …/{key}`: per workspace, workspace admin. A workspace
  value may only be **lower** than the global one.

Each limit returns `{key, value, default, source, min, max, unit, description, group}`. Every
change is written to the audit table.

### B2. Usage per user
- `llm_call.user_account_id` (nullable FK, `ON DELETE SET NULL`, indexed).
- Fill it wherever an AI call is recorded and a signed-in person caused it. Background and CLI
  calls stay NULL ("system").

Table `model_price`:
- `provider`
- `model`
- `input_per_mtok_eur`
- `output_per_mtok_eur`
- `updated_by`
- `updated_at`

It is superadmin-editable and empty by default: costs show as "set a price" until filled.

`GET /api/w/{ws}/admin/usage?days=30` (workspace admin) → by user, by model, by day and by purpose:
- calls
- input tokens
- output tokens
- failures
- p50 latency
- estimated cost (EUR, `null` when the price is missing)
- average cost per call

The superadmin also gets `GET /api/admin/usage?days=30` across all workspaces, split by workspace.

### B3. Models from the provider
`GET /api/w/{ws}/ai/models`:
- Lists the models the workspace's own key can use, via Gemini `models.list` or Anthropic
  `models.list`, filtered to text-generation models and cached 1 h per workspace.
- If the key is missing or the call fails, fall back to a static list:
  - Gemini: `gemini-3.5-flash` (default), `gemini-3.5-flash-lite`, `gemini-3.1-pro-preview`,
    `gemini-2.5-flash`, `gemini-2.5-pro`
  - Anthropic: unchanged

`gemini_model` default becomes `gemini-3.5-flash`. Check that `app/llm/gemini.py`'s version checks
(`startswith("gemini-3")`, the thinking options) handle 3.5. Never log the key.

### B4. Task status `in_progress`
- Allow `in_progress` in `ck_task_status`.
- API filters and counts accept it.
- Anything that treats `open` as "not done" also treats `in_progress` that way: the Home and Summary
  counts, the overdue lists and visibility.

`PATCH` a task's status to any of `suggested`, `open`, `in_progress`, `done` or `dismissed`, with the
existing permission rules.

### B5. Tests
- the limit resolution order (workspace → global → `.env`)
- bounds and the lower-only workspace rule
- audit rows
- the limits actually applied by one or two services
- usage aggregation, including costs with and without a price
- user attribution on an assistant call
- the model list fallback without a key
- the `in_progress` status flowing through the counts

Then run `make api-types`.

## E. Public demo (PO idea, 2026-10-20)
Replaces "test workspace" for visitors.
- The sign-in page gets a **"Try the demo"** button: no account needed.
- Inside, a **"Viewing as" switcher** moves between Demo admin and the synthetic reps.
- PO decisions:
  - fully editable, **reset every night**;
  - AI works with the **visitor's own key**.

### E1. Accounts and sessions
- Setting `DEMO_WORKSPACE` (default `test-data`). The demo is on when that workspace exists and
  `is_demo`; `/api/auth/status` returns `demo_available`.
- `user_account.is_demo BOOLEAN NOT NULL DEFAULT false`:
  - **Demo admin** account: membership `admin` of the demo workspace, never superadmin.
  - The reps' accounts from `backfill_logins` are marked `is_demo` too.
  - Demo accounts never have a password and never sign in through `/login`.
- `POST /api/auth/demo` `{as?: "admin" | <app_user_id of a rep in the demo workspace>}`.
  - Public. Rate-limited per client address, e.g. 20 per hour.
  - Issues a normal session cookie for that demo account, with `user_session.is_demo = true`.
  - Called while signed in to a demo session, it switches identity: the old demo session is ended
    and the new one keeps the session-scoped AI key (E3).
  - It never applies to a non-demo session.
- `GET /api/auth/demo/identities` (demo session only) → `[{as, label, role}]` for the switcher.
- Demo sessions last at most 4 hours.

### E2. Guardrails
Server-side: one helper `is_demo_session(request)`. Each blocked action returns 403 "not available
in the demo".

Blocked:
- creation codes, join tokens, invitation emails
- people and access (members), password changes and the forgot flow for demo accounts
- connectors (TamTam, Gmail/Outlook mailbox, external database connections)
- workspace AI settings (the stored key)
- deleting or creating workspaces
- admin limits and prices (read-only view is fine)
- uploads larger than 2 MB, at most 20 files a day in the demo

Everything else is allowed: CRM edits, notes, tasks and the Kanban, flows, workbooks, scans,
models.

### E3. AI in the demo
- The visitor can paste their own provider key in a "Demo AI key" dialog, opened from AI settings
  or from the assistant.
- It is sealed in `user_session.llm_key_enc` with provider and model, and is never written to the
  workspace.
- LLM calls in a demo session use only that key. Without it, AI shows "Add your own key to try AI
  in the demo".
- The key is deleted when the session ends, at sign-out and at the reset.
- Usage rows record the demo account.

### E4. Nightly reset
- Command `dataforce demo reset` rebuilds the demo workspace from seed 42, in the same order as
  today: testdata, then activities, then logins.
- It builds under a temporary slug, then swaps in one transaction:
  1. delete the old workspace (cascade);
  2. rename the new one to `DEMO_WORKSPACE`;
  3. re-link the demo admin and the rep accounts' memberships;
  4. delete all demo sessions.
- On Cloud Run: a **Cloud Run job** with the same image, triggered nightly at 04:00 Europe/Paris by
  Cloud Scheduler. Documented in HOSTING-PLAN §3.5. The lead sets it up with the PO.

### E5. Onboarding
- The `/welcome` "Test workspace" card stays for the superadmin only.
- Credit holders (creation-code sign-ups) only create real workspaces: the API refuses
  `kind="test"` for them.

### E6. Frontend
- "Try the demo" under the sign-in form, shown when `demo_available` (local and hosted).
- The old demo-rep chips are removed: the switcher replaces them.
- Top bar in a demo session:
  - a yellow "Demo · resets nightly" mark;
  - a "Viewing as: Demo admin ▾" menu listing the identities;
  - "Exit demo" signs out.
- Blocked actions are hidden or disabled with a one-line reason.
- The assistant offers "Use your own key" in the demo.

### E7. Tests
- Starting a session and switching identity.
- A non-demo session can never switch.
- Every blocked route refuses a demo session.
- The demo AI key stays per session and never reaches the workspace table.
- The reset swap keeps the demo accounts working.
- Rate limit on `/api/auth/demo`.
- No empty-password path is opened.
